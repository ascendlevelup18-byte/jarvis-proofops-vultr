Story Runs Library Method

Recorded evidence — not a live execution.

An agent can reach checkout and still be wrong.

A model's report that a task is done isn't proof of the business result. So in ProofOps, the model only proposes, separate code decides, the browser runs in isolation, and an independent check reads the store's own records.

  1. AI proposalA live model proposes one of five typed actions.
  2. Deterministic authorizationPolicy code decides. A person approves the exact cart for any order.
  3. Isolated executionChromium in gVisor, with no network except a gateway limited to this run's store.
  4. Independent verification and evidenceStore records are compared with expectations frozen before the run, and every file is checksummed.

How to read this evidence

What the mechanism is

Unkeyed SHA-256 file checksums, with a separately recorded hash of each manifest as its anchor.

  • No HMAC.
  • No KMS signature.
  • No off-host immutable attestation.

Someone who could rewrite both the files and the anchor could defeat this. The check shows consistency, not who produced the files.

Two separate results

Mission outcome
PASS, DESIGNED FAIL or INCOMPLETE. What the verifier recorded about the task.
Evidence integrity
ANCHOR VERIFIED, INCOMPLETE or TAMPERED. Whether the files match their checksums and recorded hash.

A designed FAIL with verified evidence is a good result: the system caught the fault, and the record is consistent.

node --no-warnings proof/verify-all.mjs

What this doesn't show

  • It's a synthetic store, not a real merchant, with no real payments.
  • The model ignoring a hostile page in recorded runs isn't a measured resistance rate.
  • The scripted forced-proposal test is separate from the live runs. The live model didn't make those proposals.
  • No third party has audited this system.
